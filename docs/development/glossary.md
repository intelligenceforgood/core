# Glossary

_Last Updated: 2026-03-19 | Last Verified: March 2026_

Common terms and abbreviations across the project. Keep entries short and link to the authoritative doc or schema.

## Core Platform

- **Case** — A single scam incident record in the system. "Case" and "review" are used interchangeably in the codebase; the canonical API noun is `review` (endpoints under `/reviews/`), but product UI and documentation use "case." The underlying SQL table is `cases`.
- **Ingestion pipeline** — End-to-end flow from classified payload to structured store, SQL dual-write, and optional vector/Vertex fan-out. See [tdd.md](tdd.md#6-ingestion-flow-canonical) and [architecture.md](../design/architecture.md).
- **Intake** — A raw victim-submitted report that enters the system via the `/intakes/` API before enrichment and case creation. Distinct from ingestion: intake is the entry point; ingestion is the batch processing pipeline that processes data bundles.
- **Structured store** — SQLite-backed record store used for analyst console reads and worker jobs. See [src/i4g/store/structured.py](src/i4g/store/structured.py).
- **Dual-write (SQL)** — Persistence of cases/entities/documents to SQL tables alongside structured store for hybrid search. See [src/i4g/store/sql.py](src/i4g/store/sql.py).
- **Hybrid search** — Combines vector retrieval with structured filters from SQL entities; powered by `HybridRetriever`. See [tdd.md](tdd.md#7-apis-and-contracts-current-surface) and [architecture.md](../design/architecture.md).
- **HybridRetriever** — The core search engine that combines Chroma/Vertex vector search with SQL-side entity filtering. Configured per request via `SearchConfig`.
- **Intake encryption / PII vault** — Fernet encryption of victim contact fields (reporter name, email, phone, handle) on intake write; decrypted on authorized read. The encryption layer is called the PII vault; the secret key is stored in Secret Manager. See [pii_vault.md](../design/pii_vault.md).
- **Fernet token** — A symmetric encryption token (AES-128-CBC + HMAC-SHA256) used by the PII vault to encrypt/decrypt victim contact fields. Generated from the `I4G_PII__KEY` secret.
- **Sandbox** — Local dataset + stores used for development and smokes (`data/`, SQLite, Chroma). Rebuild via `i4g bootstrap local reset --report-dir data/reports/local_bootstrap`.
- **Smoke test** — Fast validation of critical paths (ingestion, search, UI) described in [cookbooks/smoke_test.md](cookbooks/smoke_test.md).
- **Dataset** — Logical label on cases/entities indicating source or tenant (e.g., `network_demo`, `dual_demo`); default comes from `ingestion.default_dataset` in settings.
- **Saved search schema** — JSON schema for `/reviews/search` requests stored in the API; refresh via `/reviews/search/schema`. See [docs/runbooks/console/search.md](docs/runbooks/console/search.md#L1).
- **Evidence dossier** — Generated report bundle with manifest and signatures; see [docs/runbooks/console/reports.md](docs/runbooks/console/reports.md#L1) and [reports/](reports/).
- **Dossier** — Assembled evidence package for a case, generated by the `dossier-queue` Cloud Run job. Includes PDF/Markdown report + manifest. Triggered manually or via case acceptance.
- **Vector store** — Embedding backend (default Chroma) holding chunked case texts for semantic search. Configured under `vector.*` settings.
- **Chroma** — Default local vector backend; persisted under `vector.chroma_dir` (e.g., `data/chroma_store`).
- **Fraud type** — Classification label on a case (e.g., `tech_support`, `romance`, `pig_butcher`); stored in structured and SQL tables.
- **Indicator** — Structured signal (bank account, wallet, email, phone, IP) captured in `indicators` table; used for structured filters.

## Fraud Taxonomy System

- **Taxonomy axis** — One of five independent classification dimensions applied to every case: Scam Intent, Delivery Channel, Social Engineering Technique, Requested Action, Claimed Persona. See [fraud_taxonomy_tdd.md](../design/fraud_taxonomy_tdd.md).
- **Taxonomy version** — Semantic version string (e.g., `v1.0`, `v1.1`) stamped on every classification result. Adding a label is non-breaking; renaming or removing is breaking and requires migration.
- **LLM tagging job** — The `classification-sweeper` Cloud Run job that runs the few-shot LLM classification pipeline to tag pending cases across all five taxonomy axes. Scheduled every 5 minutes in production.

## TIFAP (Threat Intelligence & Fraud Analytics Platform)

- **TIFAP** — Threat Intelligence & Fraud Analytics Platform. The analytics subsystem inside `core-svc` that aggregates pre-computed statistics, runs campaign detection, and provides the impact dashboard. Operates via direct SQLAlchemy reads (no HTTP hop). See [threat_intelligence_analytics_tdd.md](../design/threat_intelligence_analytics_tdd.md).
- **Entity link** — Structured association between a case and a threat entity (wallet address, domain, phone number, etc.) stored in the `entity_links` table. Powers the intelligence graph.
- **Indicator registry** — The `indicators` table in SQL that catalogs structured threat signals extracted from cases. Deduplicated + normalized.
- **Campaign** — A correlated cluster of cases attributed to a single threat actor or operation. Detected automatically via graph clustering (Louvain algorithm) and manually annotated by analysts. Stored in the `campaigns` table.
- **Threat score** — A numerical risk rating computed for campaigns and entities. Aggregates case severity, recency, financial loss, and indicator density.

## SSI (Scam Site Investigation Service)

- **Investigation** — A single automated inquiry into a URL. SSI runs three phases: Passive Recon (WHOIS, DNS, VirusTotal), Active Interaction (browser automation), and Intelligence Synthesis (LLM analysis). Each investigation produces a `ScanResult`.
- **Playbook** — A named, configurable SSI investigation strategy stored in the `ssi_playbooks` table. Defines scan depth, enabled probes, and interaction behavior.
- **AWH (Automated Web Hunter)** — The previous codename for the SSI investigation pipeline before the February 2026 merge into `ssi-svc`. References to AWH in code/docs refer to the same service.
- **eCX (eCrimeX)** — The APWG eCrimeX threat intelligence clearinghouse. SSI submits qualified scam-site evidence to eCX as structured submissions, and polls eCX to trigger investigations of inbound indicators. See [tdd_ecx_integration.md](../../../ssi/docs/tdd_ecx_integration.md).
- **Live monitoring** — WebSocket-based real-time event stream for SSI investigations. The `ssi-svc` emits investigation phase events; the console displays them as a live activity feed. Also exposed as an SSE proxy via core-svc at `/events/ssi/{scan_id}`.
- **Evidence bundle** — The complete output package from an SSI investigation: screenshots, network captures, extracted wallet addresses, risk score, and LLM analysis report. Stored in GCS bucket `i4g-{env}-ssi-evidence`.
- **Dossier generation trigger** — The `triggerDossier` flag in an SSI investigation request. When set to `true`, a successful investigation automatically enqueues the associated case in the dossier generation pipeline.

## Infrastructure

- **Cloud Run service** — A long-running HTTP container that serves requests (e.g., `core-svc`, `i4g-console`, `ssi-svc`). Scales to zero when idle.
- **Cloud Run job** — A short-lived container that runs a task to completion (e.g., `ingest-bootstrap`, `classification-sweeper`, `ssi-ecx-poller`). Triggered manually or by Cloud Scheduler.
- **IAP (Identity-Aware Proxy)** — Google Cloud's authentication layer in front of Cloud Run services. Validates browser sessions via OAuth2, injects `X-Goog-Authenticated-User-Email` and `X-Goog-IAP-JWT-Assertion` headers. Only enabled on services in cloud environments.
- **Service account** — A GCP IAM identity used by a Cloud Run service or job to authenticate to other GCP services (Cloud SQL, GCS, Secret Manager). Each service/job has a dedicated service account (`sa-app`, `sa-ssi`, `sa-ingest`, etc.).
- **Workload Identity Federation** — A GCP mechanism allowing GitHub Actions to authenticate as a service account without a key file. Used in CI/CD to push Docker images and trigger deployments.
